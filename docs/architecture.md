# LLM 主导创作架构

## 创作责任

用户只输入 `ideas`、`points`、`style`。LLM 决定书名、题材、单章目标长度、主配角与反派、地图、冲突、成长体系、升级代价与限制、分卷、结局方向、阶段目标、发展策略及验收项。程序负责执行、持久化和一致性约束，不代替模型预设固定题材或升级路线。

新作品先保存创作种子，`stage=0`、`status=idea`，此时没有虚构的阶段记录。构思成功后，`CreativeBlueprint` 与第一阶段在同一事务提交，状态改为 `writing`。`WorldDesign` 保存完整角色、地图和体系，`StageDesign.development` 描述每个阶段的人物与体系升级策略，`exit_hook` 描述后续承接。

## 执行流程

```text
网页 / CLI / HTTP API
           ↓
StoryService.step（完成下一章或决定完结）
  ├─ 无创作方案 → conceive
  ├─ 阶段已验收 → direct → 新阶段，或 completed
  ├─ 无下一章规划 → plan（LLM 决定 1–8 章近程规划）
  └─ write → 叙事导演 → 主笔 → 独立文学审稿 → 事实审核 → 采纳
                            └─ 有定位的改稿意见 → 带完整原稿修订（最多两轮）
                   ├─ 审核结构错误 → 保留正文，最多重审两次
                   └─ 实质内容矛盾 → 最多两次正文修订 / 失败
           ↓
Repository → SQLite

AutoRunner → 重复同一个 step，提供后台任务、暂停和心跳
create_model → 根据 SCRIPTOR_PROVIDER 选择传输
  ├─ ResponsesModel → POST /responses
  └─ AnthropicModel → POST /v1/messages
```

手动与自动模式采用同一流程。手动模式每次点击推进到一章完成；自动模式重复推进，用户不再需要填写下一阶段。到达正文证据支持的阶段里程碑后，由 `Direction` 判断下一阶段或完结；单纯的大纲计划不能触发验收。

## 数据与兼容

| 表 | 职责 |
| --- | --- |
| `books` | 创作种子、生成元信息、完整设定、当前阶段、状态、乐观锁版本 |
| `stages` | 目标、地图、验收项、发展策略与后续承接 |
| `plans` | 按书籍与章节唯一的场景规划 |
| `chapters` / `revisions` | 当前采纳的正文和审核 / 追加保存的历史版本 |
| `runs` | 操作结果、失败候选、审核、上下文选择、响应 ID 和 token 用量 |
| `jobs` | 自动任务状态、本次章数上限、已新增章节、当前步骤、错误和运行租约 |

Schema 为 `PRAGMA user_version=2`，启动时从 v1 增加任务表与索引，不删除或改写旧作品。旧 `{book,stage}` 请求和旧高级接口兼容。旧版文件夹格式不自动导入。

## 提交与修订

每个构思、规划、导演或写章操作独立落库；后续失败不撤销已经成功的步骤。生成前取得快照，完成后用 `books.revision` 比较并提交，模型调用期间不持有写锁。正文、导演调整后的实际规划、文学与事实审核、叙事状态、版本历史与成功运行记录在一次事务中写入。

新章只能顺序写入；当前阶段最新一章可显式编辑，重写后删除依赖旧正文的后续未写规划。网页附带 `expected_revision`，阻止旧页面覆盖新版本。已完结作品只读。

审核使用 `SourceReview`，存储仍使用原有 `Review`，不改变旧作品格式。`evidence.py` 将完整正文划为原样片段，保留 id/start/end；长行按句子边界尽量切分到每片段不超过 360 字符。所有非空正文都交给模型，不截取开头，也不对原文作模糊匹配或标点归一化。

模型通过 `source_id/source_ids` 选择支撑事实的片段，通过 `criterion_id` 选择验收项；程序提取真实原文、恢复验收项原名并排序，然后继续执行原文连续子串和唯一标识校验。不存在的编号、漏项、重复项和不合格结构触发 `EvidenceError`，在同一份正文上最多再审核两次，不交给作者重写。

`runs.artifacts.evidence_sources` 保存定位信息，`review_attempts` 保存每次审核输出、错误与结果。只有实质内容矛盾进入作者修订循环，最多重写两次；手动请求的网络故障按 SDK 有限重试后返回；后台对网络、429、5xx 故障另有有限等待重试，不无界循环。

正文生成后存储创作指纹：用户种子、完整设定、各阶段、当前规划及前文版本。因审核结构、接口失败或暂停留下的候选，下一次 `step` 只有在指纹一致时才可复用；书籍的操作版本号不参与指纹，因此新自动任务启动不会无谓丢弃可恢复的候选。已知内容矛盾或指纹变化的候选不会自动恢复。没有指纹的旧候选可手动载入重新审核。

## 任务生命周期

`running → stopping → paused`，或 `running → completed / failed`。`completed` 指本次运行结束，可能达到本次章数上限，也可能是故事完结；全书状态以 `books.spec.status` 为准。没有无界生成，单次任务新增上限为 1–500 章。

网页发起后立即返回任务 ID，任务在服务进程的后台线程执行；浏览器关闭不会停止它。网页轮询任务和作品，用户也可从另一窗口读取进度。生成、全文审核和证据修复均有可见的阶段名称。暂停在模型调用之间检查：当前调用完成后，下一阶段不再启动；已有候选通过失败运行记录保存，已审核结果则原子提交。

一个作品最多一个活动任务，由 SQLite 部分唯一索引和事务保护。活动任务期间手动写操作拒绝；启动任务同时提升作品版本，使此前尚未提交的手动候选过期。

任务每 5 秒续租，租约为 30 秒。进程退出或失去心跳后，过期任务在查询或再次运行时标记为 `interrupted` 并解除占用；过期工作线程在提交时也必须通过租约检查。服务器重启不自动发起新的付费调用，用户再次运行即可从现有正文继续。正常关闭会请求暂停；强制结束时仍在内存中的生成内容不保证恢复。

CLI 自动运行使用同一任务机制，终端保持运行；Ctrl+C 请求暂停并等待当前步骤。任务记录持久化，但没有外部进程守护器、分布式队列或自动重启调度器。

## 记忆与上下文

事实按 `(kind,key)` 标识，按当前采纳版本回放，覆盖人物状态并保留事件与伏笔，不混入旧版本或未来规划。阶段验收在当前阶段逐项累积，仅采纳审核置信度至少 0.8 的本章证据。

必需上下文包括创作种子、完整设定、当前阶段与场景任务；正文生成和审核使用前章全文（超过 12000 字符则保留末尾 8000 字符）、叙事接力状态、词项检索到的事实和历史摘要。必需材料放不下时明确失败，不悄悄丢掉前情。审核为完整正文预留字符预算，不截断正文；预算不足时保留候选并报错。

字符预算不是 token 上限；中文双字词项检索不是语义向量检索，可能漏召回。引文存在也不等于语义蕴含。模型的自我审核、阶段判定与结局判定仍可能错误，记录和编辑功能用于人工检查。

## 验证范围

离线测试验证三字段输入、自主角色与体系设计、手动推进、LLM 阶段切换与收束、修订次数上限、自动任务暂停续跑、排他运行、过期租约拒绝提交、v1 数据库升级，以及原有事务与 Responses 格式。

浏览器测试使用临时数据库与假模型，覆盖完整新建、创作、编辑恢复、后台运行和手机布局。尚未验证真实模型的长篇文学质量，也没有多用户鉴权、流式输出或任意历史章节的依赖重写。

## 叙事质量流程（0.5）

`narrative.py` 将逐章创作拆成 `NarrativeBrief → 正文 → LiteraryReview → 定向修订`，之后才进行 `SourceReview` 事实审核。叙事导演可替换尚未发生的粗略安排；用户种子、已发生事实和硬规则保持约束。每场包含触发原因、欲望、阻力、选择、后果与情绪转折，并明确本章读者回报、当下压力、对方主动行动及不可撤回的局面变化。

文学审稿独立调用，看到完整编号正文与前情；有重大问题、客观连续性矛盾（即使被审稿标作 minor）、任一维度低于 3 或明确要求修改时进入修订。问题必须能定位到真实片段；审稿结构错误只重审同一稿，不触发改写。最多两轮正文修订，文学不通过直接停止，不进入外层事实矛盾的重新写作循环。用户手动稿不允许自动改写。

审稿不是可靠的客观裁判。真实试写中出现过“实际仍拖沓但自评通过”的样本，因此提示包含停滞反例，并要求检查相对前章的净变化；仍需人工阅读和更长程评估。

`Review` 新增可选 `literary_review`、`narrative_state`，旧 JSON 兼容，无需数据库迁移。叙事状态记录实际事件而非计划。`runs.artifacts` 保存导演方案、每版完整稿、每次审稿及最终结果；创作指纹包含流程版本，防止自动恢复旧流程的低质量候选。

## Anthropic 接入（0.6）

提供商在启动时显式选择。`Settings.from_env` 分别读取 `OPENAI_*` 或 `ANTHROPIC_*`，两组配置不串用；`create_model` 用于网页请求、CLI、后台任务和真实模型复测脚本。旧配置未设置 `SCRIPTOR_PROVIDER` 时继续使用 OpenAI Responses。

两个适配器共享 `text/structured/close` 合约与完整 Pydantic 本地校验。0.6.2 起 Anthropic 默认使用 `tools` / `tool_choice` 指定唯一的 `submit_result`，从其 `input` 读取结构化数据。不会执行工具。`ANTHROPIC_STRUCTURED_MODE=json_schema` 仍可显式使用 `output_config.format` 和 SDK 的 `transform_schema`；`json` 模式使用完整 JSON 合约提示。所有模式都执行原始 Pydantic 约束。`SCRIPTOR_STRUCTURED_OUTPUT=false` 强制 JSON 文本模式。

正文与 JSON 文本要求 `end_turn`；工具结构化模式要求 `tool_use` 和唯一同名的 `submit_result` 参数对象。忽略 thinking 块；拒绝截断、拒绝、意外工具、多个工具及空响应。token 总数计入输入、输出及缓存输入；网络与 HTTP 错误统一包装，不向页面暴露响应正文或密钥。SDK 最多重试两次，不自动切换提供商。健康检查返回实际 `provider/api_format`。

真实 Anthropic Python SDK + HTTP MockTransport 测试覆盖请求路径、认证头、system/messages、Schema 转换、本地校验、各种停止原因、错误信息、用量，以及导演→主笔→文学审稿→事实审核的完整写章流程。0.6.0 发布时本机尚未配置 Anthropic 凭据；0.6.2 的真实中转验证与兼容性缺陷见 [Anthropic 兼容性排查](anthropic-compatibility.md)。

## 暂时故障恢复（0.6.1）

`TransientModelError` 区分网络连接、超时、429 与 5xx；401、403、404、参数拒绝、结构化数据错误和文学退稿不进入后台临时故障重试。错误提示分别指向认证、权限、路由、参数或上游可用性，503 不再笼统建议检查 Schema。

SDK 仍最多重试两次；后台在 SDK 抛出暂时故障后，默认最多额外重试当前 `step` 两次，等待 5、10 秒。数字 Retry-After 可提高等待时间，每次最多 60 秒。没有额外无限重试层。每章成功后重置后台计数，失败不增加完成章数；持续故障耗尽次数后停止。

等待期间更新任务步骤，保持续租，轮询暂停请求。重试重新读取已提交的构思、规划和前文；符合创作指纹的已有正文候选通过既有恢复机制重新审核，不重复生成已保存的候选。事务、事实审核与文学审核不变。

最终 HTTP/连接失败也写入调用记录，包括提供商、模型、状态码、错误类型和合法的请求编号；不保存响应正文、认证头或密钥。离线测试隔离真实 .env 和提供商环境变量，避免切换提供商后测试意外访问付费端点。

## 结构化传输与诊断（0.6.2）

原生 `output_config` 被部分中转忽略时，HTTP 200 也可能返回 Markdown。默认工具参数模式避免把普通说明文当 JSON 解析；JSON 模式额外在提示中提供完整 Schema。完整的 JSON 外层代码围栏可以确定性移除，但不会从散文中截取片段、推测缺失字段或修复截断内容。

调用记录增加请求模式、Schema 名称、输入字符数、输出上限及字段错误路径；不记录请求认证信息。最终结构化校验失败时，原始方案单独保存在本书运行记录的 `structured_candidate` 中，便于检查，不写入设定、正文或事实记忆。网页可查看调用诊断和失败方案。
