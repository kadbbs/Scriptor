# 叙事流程验证

验证日期：2026-10-19。版本：0.5.0。

## 问题与改动

实际阅读本地作品发现，旧近程规划将问话、辨识、取样、记录和申请炉具拆成多个章节，人物反复讨论操作边界，能力展示和具体结果长期延后。旧作者上下文只保留前章摘要和末尾 1000 字符，很难承接前面的人物动作与对话。

新版增加逐章叙事导演、独立文学审稿和基于完整原稿的定向修订；保留前章实际正文与叙事状态。导演可以重排未发生的弱规划。事实抽取继续独立处理，小说人物可以猜测、犯错、试招，不能因记忆需要严谨就让所有人物变成审核员。

## 真实模型与人工阅读

测试使用本机配置的 Responses 模型，先对实际数据库作只读备份，再在副本上续写。原始作品没有改写。完整正文、各版候选、审稿与本地评估数据库留在被 Git 忽略的 `data/evaluations/` 中。

在同一前文和旧规划上生成了旧流程基线，并试跑新版。第一次新版试写虽然补充了操作场景，仍明显拖沓，出现大量重复确认和“不能证明什么”的问答；模型却给出通过。人工阅读没有接受这个结论，进一步补充停滞反例、相对前章的净变化、特殊背景主角的实际能力兑现等标准。后续试写实际触发文学退稿与原稿修订。

旧书副本随后连续完成第 3、4 章，分别 2444、4221 字符。第 3 章经历三版正文、三次文学审稿；第 4 章承接样本和炉具问题，增加了送草人的配食损失、主角复称选择及其责任代价。两章都通过事实与原文引用审核。人工阅读仍发现流程对白偏多，第 3 章仍偏平，不能把“模型通过”当作问题已经全部解决。最终又增加当下压力、对方主动行动和不可撤回变化三个导演字段，并明确虚构技艺按小说规则产生效果。

使用同一创作种子从零构思的第一章为 5497 字符，经一次定向修订后通过。修订修复了“手麻病患与外出指路者被写成同一个人”的身份矛盾，并压缩末段复述。人工阅读可见“叫停可疑食物→损失当晚口粮→对手用救济交换草场和控制火源”的因果链，配角的生计与控制权动机更清楚；主角技艺兑现不足仍需要后续检查。

从零作品的第二章在最终导演字段和虚构技艺指引下完成：主角以余火、破碗和当地食根进行有限处理，使一名病患能进食并稍缓腹痛；同时耗损食材、裂碗，对手搬走炭火，把结果变成下一章的新压力。文学审稿指出食根分配的数量矛盾，却标成 minor 放行。由此进一步把客观连续性矛盾设为必须修订，不能因 minor 标签绕过。人工修正数量后复审又指出“煨软食物不能充分解释缓痛或兑现丹王能力”。随后保留原稿自动修订两轮，最终 3377 字符通过文学和事实审核：补出分离硬筋、调成薄糊的过程，结果收窄为能吞咽，腹痛仍在。人工阅读认为这一版仍偏保守，因此最终提示进一步明确：不把叙事因果当临床验证，不以撤回全部回报代替修复。该提示调整还需要更长程试写，不能据此宣称文学问题已全部解决。

中间一次试跑还遇到真实端点 HTTP 503，候选保留在副本运行记录中；该故障不能作为文学质量的判断依据。

这是一部作品的少量章节验证。独立调用的审稿仍使用同一配置模型，模型分数与“通过”不是客观可读性指标，也不构成长篇质量评测。最终仍需阅读全文，核对具体行动、后果和人物声音。

## 自动化检查

Python 3.10、3.12 各通过 65 项离线测试。新增覆盖：有定位的因果问题导致原稿修订、手动稿不自动改写、文学修订上限、不存在的审稿编号在同稿上修复、失败不提交正文、实际规划和叙事状态提交、前章开头及末尾保留、矛盾的审稿分数不能绕过质量门槛。

Chromium 烟测通过建书、手动推进、文学审稿与叙事接力显示、草稿恢复、编辑失败候选、历史、记忆、阶段切换、后台自动运行、导出与手机布局。Ruff 与格式检查通过。

## 自行复测

```bash
# 显式调用真实端点，会产生模型费用；在空目录中复制数据库后续写两章
uv run python -m tests.evaluate_narrative \
  --book-id BOOK_ID \
  --output data/evaluations/my-run \
  --chapters 2
```

输出目录必须为空。脚本导出每章 Markdown 和对应完整运行记录；失败时导出最后运行，便于检查候选与具体审稿意见。不会向 Git 添加用户正文或密钥。
